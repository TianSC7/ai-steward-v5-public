# 少往返工作法（派工单固定段）

`scripts/factory_runner.py` 的 `work_brief` 拼装里固定插入一段 `BUILD_METHOD_NOTE`（模块级字符串常量），
位置在文件行号地图 `{map_md}` 之后、`## 规格正本` 之前。每个施工轮次的派工单都会带上这段，无需厂长逐单手写。

## 为什么加

工厂订单慢的根因在轮内结构，不在机器也不在吐字：

- 实测样本（2026-11-26，AA 的 ZCode 用量库逐次调用拆账，G60 第 2 轮施工）：
  **81 次模型调用、模型时间合计 1187 秒**，其中**首字等待合计 689 秒 = 58%**；
  本地工具（Bash / Read / Edit / Write）合计只占 **121 秒**。
- 也就是说，时间主要花在「调用次数 × 每次首字等待 5–9 秒」上，而调用里很大一部分是
  一次只读一处、改一处就回看一次、查一次 git 的小步动作。
- 这些浪费不是工人能力问题，而是提示词里没有成体系的工作法：旧派工单只有一句
  「按地图行号区间定向读取，用一次性集中编辑修改」，约束不到读取合并、改动合并、验证合并与交卷附录。

因此把工作法固化进派工单固定段（五条：开工一次读够 / 读取并成一条命令 / 改动合并落盘 /
验证一次做完 / 交卷一次写清），并明确「以做对为准：拿不准的地方先读再改，不许为了省调用跳过验证或漏做断言」，
防止提速被误读成省验证。

## 怎么量效果

数据源：AA 的 ZCode 用量库（`~/.zcode/cli/db/db.sqlite`，逐次调用记录含模型时间与首字等待）。

1. 取合入前后**各 10 轮**同一产线（同 kind、同模型档）的施工轮次。
2. 每轮统两个数：
   - **模型调用次数**（轮内 `model_request_count` 合计）；
   - **首字等待合计秒数**（每轮 sum(first_token_latency)）及占模型时间比例。
3. 对照口径：调用次数应与首字等待同向下降；若调用数降而首字等待不降，说明瓶颈转移到单次调用的
   输出长度或长上下文，需要另查。回归口径以 F3 验收（离线测试 + 端到端）不退化为准，
   不以提速幅度作为合入闸门。
