# 提示词作战手册（PROMPT PLAYBOOK）

> 管家派单前从这里挑模板。原则：**验收标准可机械判定**；worker 看不到你和用户的对话。

## 通用骨架

```text
【任务】<动词开头一句话>
【背景】<仓库绝对路径 | 相关文件 | 已知现象 | 环境约束>
【边界】<不能碰的目录/操作；不得删除用户文件；不得外传密钥>
【验收】<命令/断言/文件存在性；必须可机械判定>
【交付】结论: 成功/失败
        证据: 命令输出摘要/文件路径/提交号
        未决: 需要用户拍板的事项（没有写"无"）
【纪律】不要问我问题；缺信息按最保守假设自行决定并在"未决"说明。
```

## T1 代码修复 → `auto-heavy`

```text
【任务】修复 <现象>，使 <验收命令> 通过。
【背景】仓库 <绝对路径>；入口 <file:line>；复现步骤 <命令>；期望 <行为>，实际 <行为>。
【边界】只改 <目录>；不改公共接口；不升级依赖大版本；不动测试夹具。
【验收】<测试命令> 全绿；且 <针对性断言> 输出 <期望值>。
【交付】附 diff 摘要 + 测试原始输出末尾 20 行。
```

## T2 代码评审 → `auto-reason`

```text
【任务】评审 <分支/PR/文件>，只找会导致线上故障的问题。
【背景】仓库 <路径>；变更范围 <git diff 范围>；运行环境 <OS/运行时>。
【边界】不改代码，只输出报告。
【验收】每个问题必须给：位置(file:line)、触发条件、影响、修复建议、置信度(高/中/低)。
【交付】按 严重/中等/轻微 三档排序；没有问题的维度也要写"未见异常"。
```

## T3 根因排查 → `auto-reason`

```text
【任务】定位 <异常> 的根因，给出可复现证据。
【背景】现象 <日志关键行原文>；时间窗 <开始-结束>；最近变更 <提交范围>。
【边界】先只读排查；需要改代码时先给计划，等我方确认后再改。
【验收】根因必须能解释全部现象；给出反证实验（改前失败/改后通过）。
【交付】结论 + 证据链（日志/提交/最小复现）+ 未解释的残余疑点。
```

## T4 资料研究 → `auto`

```text
【任务】查清 <问题>，给出可执行结论。
【背景】已知 <已有结论/链接>；关注 <版本/地区/时间范围>。
【边界】只用可核验来源；不编造链接；不确定就标注。
【验收】每条结论后附 [n] 来源；给出"如果来源错了我怎么发现"的检查点。
【交付】决策优先：先给结论，再给依据，最后给不确定性。
```

## T5 批量改写/翻译 → `auto-cheap`

```text
【任务】把 <输入> 按 <规则> 改写/翻译。
【输入】<文件路径或原文>
【规则】<术语表 | 风格 | 长度限制 | 禁止项>
【验收】输出条数与输入一致；术语命中率 100%；无新增事实。
【交付】只输出结果，不要解释；结尾给一行计数。
```

## T6 验收复核（红队）→ `auto-reason`

```text
【任务】你是验收方，不是实现方。判定 <任务> 是否真的完成。
【背景】实现方声称：<原话>；证据：<提交/文件/测试输出>。
【边界】只读；可以运行测试，不改代码。
【验收】逐条核对验收标准；任何一条无证据即判"未通过"。
【交付】通过/不通过 + 每条标准的证据 + 最可能被掩盖的问题。
```

## 选型对照

| 模板 | 建议别名 | 理由 |
|---|---|---|
| T1 代码修复 | `auto-heavy` | 要跨文件理解与长上下文 |
| T2 评审 | `auto-reason` | 要取舍判断 |
| T3 根因 | `auto-reason` | 要反证与因果链 |
| T4 研究 | `auto` | 长短不定，交给分层 |
| T5 批量 | `auto-cheap` | 体力活，量大 |
| T6 复核 | `auto-reason` | 需要对抗性思维 |

## 反模式

- 把"你看着办"当验收。
- 一次派单塞三个目标（worker 会挑最容易的那个做）。
- 让 worker 自己决定要不要改公共接口。
- 不写仓库绝对路径，指望 worker 猜。
